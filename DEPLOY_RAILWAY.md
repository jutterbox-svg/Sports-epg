# Deploying to Railway

This turns the project into one always-on Railway service: it serves
`epg.xml` and `epg.tar.gz` over HTTP and regenerates them every 6 hours in
the background. No separate cron job or volume needed.

## Files used for this deployment

- `Dockerfile` — Railway builds and runs this automatically.
- `web_service.py` — the process Railway keeps alive; wraps `epg_generator.py`.
- `epg_generator.py`, `channels_config.json` — unchanged from the CLI version.

## Steps

1. **Create a repo.** Put all the project files (including `Dockerfile` and
   `web_service.py`) in a git repo — GitHub is easiest since Railway deploys
   straight from it.

2. **New Railway project → Deploy from GitHub repo.** Pick the repo. Railway
   detects the `Dockerfile` automatically and builds from it — no extra
   config needed.

3. **(Optional) Set environment variables** under the service's *Variables*
   tab:
   | Variable | Default | Purpose |
   |---|---|---|
   | `REFRESH_HOURS` | `6` | How often to regenerate |
   | `SPORTSDB_API_KEY` | (uses `"3"` from the config) | Set this if you have a paid TheSportsDB key, instead of editing the JSON |
   | `OUTPUT_DIR` | `output` | Where files are written inside the container |

   `PORT` is set automatically by Railway — don't set it yourself.

4. **Deploy.** Railway builds the image and starts `web_service.py`. Check
   the *Deployments* → logs tab; you should see `"Serving output on port
   ...` followed by the first `"Starting EPG generation run..."` a moment
   later.

5. **Get a public URL.** In the service's *Settings* → *Networking*, click
   **Generate Domain**. Railway gives you something like
   `https://your-service.up.railway.app`.

6. **Point your IPTV player at it:**
   - `https://your-service.up.railway.app/epg.xml`
   - `https://your-service.up.railway.app/epg.tar.gz`

   Both are the same guide; use whichever format your player expects.

7. **Get the team list too:**
   - `https://your-service.up.railway.app/teams.csv`

   This is generated by `list_teams.py` on the same schedule as the EPG (see
   `regeneration_loop()` in `web_service.py`) and covers Premier League,
   Championship, EFL League One, EFL League Two, National League, and
   Scottish Premiership - one row per team with its ID, stadium, capacity,
   and badge URL. Edit the `LEAGUES` dict at the top of `list_teams.py` to
   add/remove leagues.

8. **Get a per-team schedule too:**
   - `https://your-service.up.railway.app/epg_teams.xml`
   - `https://your-service.up.railway.app/epg_teams.tar.gz`

   Generated by `team_epg_generator.py` - one XMLTV channel *per team*
   (across every league in `channels_config.json`) instead of one channel
   per league, so e.g. Arsenal gets its own channel showing just Arsenal's
   fixtures (titled like "Arsenal vs Brighton (H)"). This run makes one API
   call per team (~370+ teams across all 16 configured leagues), so it takes
   noticeably longer than the league-level run - expect it to still be
   working for several minutes after the other files are ready. It uses a
   longer per-request delay (`team_request_delay_seconds` in
   `channels_config.json`, default 2.2s) to stay under the free key's rate
   limit given the higher request volume.

   **Free-key limitation:** TheSportsDB's free/test key restricts
   `eventsnext.php` (the per-team endpoint) to a team's next *home* fixture
   only - away games may not show up on that team's own channel (though
   they'll still appear on the opposing team's channel, and on the
   league-wide channel from step 6). A paid key removes this restriction.

## Notes specific to Railway

- **Storage is ephemeral.** If the service restarts or redeploys, the
  container filesystem resets — but that's fine here, because
  `web_service.py` regenerates the files on startup automatically, so the
  guide is never missing for long.
- **The 6-hour refresh runs inside the process**, not as a Railway cron —
  simpler to reason about, and means the first file is ready within seconds
  of deploy rather than waiting up to 6 hours for a cron tick.
- **Hobby plan usage:** this is a lightweight process (idle between runs,
  brief burst of API calls every 6 hours) — well within Railway's free/hobby
  tier resource limits.
- If you'd rather use Railway's native **Cron Job** service type instead
  (runs `python epg_generator.py --out-dir /data --config
  channels_config.json` on a schedule and exits, rather than staying
  resident), that also works, but you'd then need a Railway **Volume**
  mounted at `/data` to persist the files between runs, plus a second
  service to serve them over HTTP — the always-on approach above avoids
  that extra complexity. Ask if you'd like that variant instead.

## 9. API-Football team schedule (optional, separate from everything above)

This is a *separate* team-only schedule sourced from API-Football instead of
TheSportsDB — built around its free tier's 100 requests/day limit, so it
refreshes once every 24 hours rather than every 6.

- Sign up for a free key at https://dashboard.api-football.com (or via
  RapidAPI — see `auth_style` in `apifootball_config.json` if you go that
  route instead).
- Set the `API_FOOTBALL_KEY` environment variable in Railway's Variables tab
  to your key (don't commit it into `apifootball_config.json` in the repo —
  the env var overrides it at startup).
- Redeploy. On first run it resolves League One/Two's IDs and fetches all
  ~96 teams' fixtures — check the logs for `"API-Football team schedule
  complete"`. After that, most runs only re-fetch fixtures (team lists are
  cached for 30 days), so daily usage stays around 96 of the 100 allowed.
- Get it at:
  - `https://your-service.up.railway.app/epg_teams_apifootball.xml`
  - `https://your-service.up.railway.app/epg_teams_apifootball.tar.gz`

If the free plan's 100/day quota is hit mid-run (e.g. from testing calls
elsewhere on the same key), the run stops early and reuses each team's last
successfully-fetched fixtures for the rest — so the guide stays complete,
just possibly a day stale for a few teams, rather than breaking. Without
`API_FOOTBALL_KEY` set, this step is skipped automatically (logged once, not
retried) and everything else keeps working as before.
